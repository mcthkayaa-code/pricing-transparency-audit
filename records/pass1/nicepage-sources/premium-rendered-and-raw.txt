NETWORK / RENDERING NOTE (important - resolves an apparent price discrepancy):
The page's own JS embeds the true base prices as plain JSON:
  baseLicensePrices      = {"personal":"89","business":"169","pro":"269","ultimate":"439"}
  baseSubscriptionPrices = {"personal":"6.75","business":"12.75","pro":"18.75","ultimate":"31.75"}
The server-rendered HTML for each plan card uses a "dollars-big, cents-superscript, no
decimal point" style, e.g. for Personal:
  <div class="price original-price personalOriginalPrice">
    <sup>$</sup><span class="price-label">6<sup>75</sup></span><span class="price-year">/mo</span>
  </div>
When a plain-text serializer (WebFetch's summarizer, or DOM .innerText) flattens the
<sup>75</sup> onto the "6" with no separator, "$6.75/mo" is misread as "$675/mo". This
is confirmed NOT a currency/geo artifact: grepped the full page JS for
currency/country/TRY/multiplier/exchangeRate/convert logic and found none — the only
"country"-related code is Amplitude/analytics event tagging (getCountryCode()), it does
not branch pricing. The static curl fetch (US Accept-Language header) returned the
identical "6<sup>75</sup>" markup, and the visual screenshot confirms a human reader sees
"$6.75/mo", not "$675/mo". CODING USES $6.75 / $12.75 / $18.75 / $31.75 per month
(billed annually) as the true, vendor-published figures. No non_usd finding applies (all
figures are USD $, no locale-based price switching detected) - D-003 check satisfied.
